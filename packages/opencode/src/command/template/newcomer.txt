## Project overview
Use a Markdown table with the columns `Topic` and `Summary`. Explain the project's purpose, primary users, and main technology in concise cells.

## Major components
Present the codebase guide as a compact Markdown table that renders clearly in the terminal. Use these columns: `Category`, `Paths`, `What it contains`, and `What to do`. Include rows for `Entry points`, `Configuration`, `Tests only`, `Documentation`, and `Skip initially`; use `Not found` when a category does not exist. Add other project-specific rows, such as frontend, backend, or application logic, when useful. Put repository paths in backticks and keep every cell concise. For the `Documentation` row, summarize what files such as `README.md` tell the newcomer instead of merely listing them. For `Skip initially`, name code the newcomer does not need to understand fully yet and explain why it can wait.

## Where to start
Use a Markdown table with the columns `Order`, `Path`, and `What to learn`. Put the most important entry-point files in a useful reading order.

## What to skip for now
Use a Markdown table with the columns `Path or area`, `Why to skip it`, and `When to revisit`. Include generated code, build output, vendored dependencies, or low-level areas that are not useful for an initial understanding.

## Representative feature flow
Trace one representative feature or request through the codebase in order. Use a Markdown table with the columns `Step`, `File or function`, and `What happens`. Only describe relationships verified from the code.

## Suggested next steps
Use a Markdown table with the columns `Step`, `Action`, and `Expected outcome`. Keep the sequence short and concrete.

## Development setup
Present a Markdown table with the columns `Task`, `Command`, `Run from`, and `Notes`. Include installation, development, focused testing, linting, typechecking, and code generation only when applicable. Copy commands from executable project sources such as package scripts, task files, or CI configuration; do not guess commands. Clearly mark prerequisites and commands that require external services.

## First contribution ideas
Present two or three low-risk starter areas in a Markdown table with the columns `Area`, `Why it is approachable`, `Start with`, and `How to verify`. Recommend only areas supported by the repository structure. Prefer isolated documentation, tests, messages, configuration, or small leaf features over core orchestration, generated code, migrations, security-sensitive code, or broad refactors. Do not claim that an issue exists or that a change is needed unless the repository provides evidence.

Match the requested experience level throughout the response. For beginners, use plain language, define necessary technical terms, avoid unexplained jargon, and favor orientation over implementation detail. For intermediate users, use standard development terminology and connect the major implementation pieces. For advanced users, be concise and technically precise, including relevant functions, abstractions, control and data flow, and tradeoffs. At every level, cite real repository paths and distinguish verified facts from reasonable inferences.
